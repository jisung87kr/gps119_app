# ADR-0005. 모든 신고는 행사(Project)에 소속된다 — "상시 운영" 기본 행사 흡수

- 상태: Accepted
- 날짜: 2026-07-29
- 관련: `epics/realtime-dispatch-control/`, ADR-0002(행사 스코프 역할), `app/Models/Request.php`, `app/Models/Project.php`

## 배경 (Context)

GPS119에는 두 종류의 신고가 공존한다.

- **행사 신고** (`requests.project_id` 있음): 참가자가 행사 QR/입장코드로 들어와 발생. 실시간 관제(`event.{id}.control`)에 표시된다.
- **일반 신고** (`requests.project_id = null`): 행사와 무관하게 `/requests/create`(slug 없음)로 발생하는 길가·야외 단발 구조요청. `requests.global` 채널로 흐르며 **관제에는 뜨지 않는다.**

운영 측면에서 이 이원화가 문제였다.

- 관리자가 "일반 신고"와 "행사 신고"를 구분해서 봐야 해 혼란스럽다.
- 실시간 관제는 행사 스코프라 **일반 신고를 구조적으로 못 본다** (전체 17건 중 관제 노출은 활성 행사분 소수).
- 그러나 "행사 밖 구조요청"(로드사이드/야외 응급)은 GPS119 원래 가치의 절반이라 **단순 제거는 부적절**하다.

## 결정 (Decision)

**신고는 항상 하나의 행사(Project)에 소속된다.** 행사를 지정하지 않은 신고는 **"상시 운영"이라는 기본 행사(always-on)** 에 자동 귀속시킨다.

- `projects`에 `is_default` 플래그를 두고 **"상시 운영" 기본 행사 1건**을 시드한다. 이 행사는 **항상 활성**(먼 미래 종료일)이라 관제 목록에 상시 노출된다.
- 신고 생성 시 `project_id`가 비어 있으면(일반 진입) **기본 행사 id로 채운다** (`Request` 생성 훅 — 모든 생성 경로 커버).
- 기존 `project_id = null` 신고는 기본 행사로 **백필**한다.
- 결과적으로 **모든 신고가 행사 소속**이 되며, `project_id`는 항상 채워진다.

## 검토한 대안 (Alternatives)

- **A. 행사 신고만 운영(일반 제거)**: 개념은 가장 단순하나 **로드사이드/야외 단발 구조요청 용도를 상실** → 원래 제품 가치 훼손. 기각.
- **B. 일반/행사 둘 다 유지 + 관리화면 라벨·필터 분리**: 로드사이드는 유지되나 **개념 이원화가 남아** 혼란의 근본 원인이 그대로. 기각.
- **C. "상시 운영" 기본 행사로 흡수 (채택)**: 개념을 **"모든 신고 = 행사 소속" 하나로 일원화**하면서, 일반 신고를 상시 행사에 담아 **로드사이드 용도도 보존**. 게다가 상시 행사가 관제에 뜨므로 **일반 신고도 실시간 관측**이 가능해진다.

## 결과 (Consequences)

**긍정**
- 개념 일원화: 관리·집계·관제·채널 인가가 전부 **project 기준 하나로** 단순해진다.
- 로드사이드/야외 단발 구조요청이 **관제(상시 운영 행사)에서도 실시간으로 보인다** — 기존엔 관제 사각지대였다.
- `/admin/requests`는 여전히 전체·이력 조회 백오피스로 유지되되, "일반 vs 행사" 구분 부담이 사라진다.

**부정/비용**
- **"상시 운영" 특수 행사**가 생긴다 — 삭제·기간수정으로 항상성이 깨지지 않도록 보호가 필요하다.
- `requests.global` 채널과 project 없는 분기는 사실상 미사용이 된다(하위호환 위해 코드는 잔존 가능).

**필요 변경**
- `projects.is_default` 컬럼 + "상시 운영" 기본 행사 시드(멱등).
- `Request` 생성 훅: `project_id`가 null이면 기본 행사로 채움.
- 기존 null 신고 백필 마이그레이션.
- (선택) 백필 후 `requests.project_id`를 NOT NULL로 강제해 불변식을 DB 레벨에서 보장.
