# 04. 앱을 목적별로 나눌 것인가

> 요구: **「사용자 목적에 따라 앱을 다르게 출시해야하는지 검토(일반사용자, 행사관리자 등)」**

## 1. 결론

🔴 **나누지 않는다. 단일 앱 + 역할 기반 분기.**

단, 이 결론에는 **재검토 조건**이 있다(§5). 지금 나누지 않는 이유는 «하나가 원래 옳아서»가 아니라 **«나눌 근거가 되는 조건이 아직 성립하지 않아서»** 다.

## 2. 지금 역할이 실제로 어떻게 갈리나

| 화면 | 대상 | 라우트 |
|---|---|---|
| 행사 입장·활동 | 참가자 전원 | `/events/join`, `/events/{id}/active` |
| 신고 | 참가자 전원 | `/requests/create`, `/requests/create/{slug}` |
| 지령 수신·수행 | 구급대·자원봉사(구급) | `/events/{id}/dispatch` |
| 실시간 관제 | 상황실(controller) | `/control` |
| 회원·행사·통계 관리 | 시스템 admin | `/admin/*` |

🔑 **역할이 «사람»에 고정돼 있지 않고 «행사별»이다.** `event_participants` 피벗의 `EventRole` 이라, **같은 사람이 A 행사에서는 참가자, B 행사에서는 구급대**일 수 있다(ADR-0002).

이게 앱 분리를 어렵게 만드는 결정적 사실이다 — **앱을 역할로 나누면, 한 사람이 두 앱을 깔고 행사마다 갈아타야 한다.**

## 3. 나누지 않는 근거

### 3-1. 역할이 사람이 아니라 행사에 붙는다

위 사실. 자원봉사 구급대원이 다음 주에 참가자로 뛰는 건 흔한 시나리오다. 앱이 둘이면 **그때마다 어느 앱을 열어야 하는지 사용자가 판단해야 한다.** 긴급 상황에서 이건 실패 모드다.

### 3-2. 신고는 «전원»이 한다

구급대원도 상황실도 사고를 당한다. 참가자 앱에만 신고 기능을 두면 **운영 인력은 자기가 다칠 때 쓸 수단이 없다.** 반대로 모든 앱에 신고를 넣으면 그 부분은 어차피 중복이다.

### 3-3. 관제 전용 «앱»을 낼 이유가 없다 (단, 관제 «화면»은 앱 안에서 열린다)

> ⚠️ **2026-08-05 검토에서 이 절이 문서 간 모순의 진원지로 지목됐다.** 원래 *"웹으로 유지한다"* 한 줄이었는데, 이게 «별도 앱을 안 낸다»인지 «앱에서 아예 안 연다»인지 읽는 사람마다 갈렸다. 아래로 확정한다.

`/control` 은 PC 대화면 전용으로 설계됐고, 모바일 대응도 **«현장 지휘용 축약»**이지 상시 관제가 아니다([`2026-08-05` 결정](../realtime-dispatch-control/README.md) 참조 — 지도 전체화면 + 3단 스냅 시트).

**확정 — 세 가지를 구분한다.**

| # | 항목 | 결정 |
|---|---|---|
| 1 | 관제 **전용 앱**을 별도 출시 | 🔴 **하지 않는다** (§3-1~3-5 의 논거) |
| 2 | 단일 앱 안에서 controller 가 `/control` 을 여는 것 | ✅ **연다.** 이미 모바일 시트 레이아웃이 있고, [`03 §5`](03-push-notifications.md) 의 상황실 푸시 착지점이 여기다 |
| 3 | 상시 관제(수 시간 모니터링)의 주 무대 | **PC 웹.** 앱은 «현장에서 잠깐 보고 배정하는» 용도 |

즉 **`/control` 은 앱에서 열리지만 «웹 화면 그대로»이고, 네이티브 기능을 따로 갖지 않는다.** 앱 셸이 URL 을 열 뿐이라 여는 것 자체에 추가 비용이 없다(§3-5).

#### 🔴 여기서 딸려오는 문제: CSV 리포트 다운로드

[`01 §2`](01-webview-strategy.md) 는 관제 CSV 를 «오리진 때문에 깨지는 것»으로만 다뤘다. A안(원격 URL)을 택하면 **오리진 문제는 사라지지만, WKWebView 는 파일 다운로드를 기본으로 처리하지 않는다.** `reportUrl()` 로 여는 `/api/events/{id}/report/*.csv` 가 iOS 앱 안에서 아무 반응 없이 죽는다.

위 2번(관제를 앱에서 연다)을 확정한 이상 이건 실재하는 결함이다 → ~~미결 M-21~~ **✅ 처리됨(2026-08-06).**

선택지는 셋이었다: 다운로드 처리 플러그인 / 앱에서는 CSV 버튼을 숨기고 «PC 에서 받으세요» 안내 / 메일 발송으로 우회. **3번(상시 관제는 PC)을 근거로 «숨김 + 안내»** 로 갔다.

**구현에서 두 가지를 비틀었다:**

1. **판정 기준이 「앱인가」가 아니라 「그 셸이 다운로드를 아는가」다** — `hasNativeCapability('file-download')`.
   「앱이면 숨김」으로 짜면 나중에 셸이 다운로드를 지원해도 **웹을 다시 배포해야** 링크가 살아난다.
   웹이 앱보다 최신인 상태가 정상이므로([`07` N2](07-roadmap.md)) 판정은 «협상»이어야 한다.
   `NativeCapability.FILE_DOWNLOAD` 는 원래 이 자리를 위해 `bridge.js` 에 미리 있던 이름이다.

2. **그냥 숨기지 않고 «어디서 받는지»를 말한다.** 숨기기만 하면 상황실은 「기능이 사라졌다」로
   읽고 찾아 헤맨다. 메뉴를 열면 「앱에서는 내려받을 수 없습니다 — PC 관제 화면에서 받아 주세요」가 뜬다.

> 참고: 헤더의 기록 메뉴는 원래 `!isMobile` 로도 가려져 있었다. 하지만 그건 **뷰포트 폭** 판정이라
> 태블릿 크기 앱 웹뷰에서는 그대로 노출된다 — 「모바일이면 어차피 안 보이니 괜찮다」가 성립하지 않는다.

회귀 테스트: `tests/js/controlReportDownload.test.js` 5건. 변이 검증 2종(「앱이면 무조건 숨김」·「웹에서도 막힘」) 모두 실패로 잡힌다.

### 3-4. 유지비가 두 배가 된다

스토어 등록 2건 × 2 플랫폼 = **심사·서명·버전·개인정보 신고를 4벌** 관리해야 한다. 그리고 이 코드베이스에는 **미러 드리프트가 «지금도» 있다** — `roleMeta.js` 와 `EventRole::markerColor()` 의 색상 7개 중 4개가, *"양쪽 같이 수정"* 이라는 주석을 달아놓고도 어긋나 있다([`06 §2`](06-repo-policy.md) 에 실측표). **규율로 두 벌을 맞추는 건 이 팀 규모에서 작동하지 않는다** — 이건 회고가 아니라 열려 있는 증거다.

### 3-5. 웹뷰 + 원격 URL 이면 분기 비용이 거의 0

앱 셸은 URL 을 열 뿐이고, 어느 화면을 보여줄지는 **이미 웹이 역할로 분기하고 있다.** 앱을 나눠도 안에 든 웹은 같다 — **껍데기만 두 개가 된다.**

## 4. 그럼 사용자 경험은 어떻게 가르나

앱은 하나로 두고, **진입 직후 «지금 이 사람의 역할»로 홈을 다르게 그린다.**

```
앱 실행
  │
  ├─ 미로그인 ──────────→ 로그인 (전화번호 / 소셜)
  │
  ├─ 참여 중인 활성 행사 없음 → 행사 입장(코드·QR) 또는 일반 구조요청
  │
  └─ 활성 행사 있음 → EventRole 로 홈 분기
        ├─ participant / staff / police / volunteer_course
        │     → 위치공유 + 신고 버튼 (현 `/events/{id}/active`)
        ├─ paramedic / volunteer_medic
        │     → 지령 인박스 + 위치공유 + 신고 (현 `/events/{id}/dispatch`)
        └─ controller
              → 축약 관제 + 신고 (현 `/control`, 모바일 시트 레이아웃 — §3-3 의 2번)
```

- 역할은 `User::eventRoleIn(Project)` 가 이미 단일 출처로 제공한다
- **신고 버튼은 모든 분기에 공통으로 둔다**(§3-2)
- 여러 행사에 동시 참여 중이면 행사 선택을 먼저 — 이미 관제 SPA 에 있는 패턴
- ⚠️ **여러 행사를 맡은 상황실이 푸시로 들어올 때 「행사 자동 선택」이 지금 틀린다** → [`03 §5-1`](03-push-notifications.md) 의 딥링크 결함. 이 분기를 앱에 그리기 전에 N1 에서 고쳐야 한다

## 5. 재검토 조건 — 이때는 나눈다

아래 중 **하나라도 성립하면** 이 결론을 다시 연다.

| # | 조건 | 왜 그때는 나누는 게 맞나 |
|---|---|---|
| 1 | **B2B 납품 요구** — 행사 주최사가 «우리 브랜드 앱»을 요구 | 화이트라벨은 셸 분리가 자연스럽다. 단 이건 «역할별»이 아니라 «고객별» 분리다 |
| 2 | **구급대 전용 기능이 네이티브에 깊게 들어갈 때** — 예: 상시 백그라운드 추적, 무전 연동, 차량 단말 | 참가자 앱에 그 권한을 요구하면 **일반 사용자 설치율이 무너진다.** 권한 요구 수준이 갈리는 순간이 실제 분기점 |
| 3 | **스토어 심사에서 «상시 위치 수집»이 일반 사용자 앱으로는 거절될 때** | 운영 인력 전용 앱으로 분리하면 정당화가 쉬워진다 → [`05`](05-store-release.md) |
| 4 | 참가자 앱 다운로드가 «행사 1회용»으로 굳어져 재설치 마찰이 문제가 될 때 | 이때는 오히려 «참가자는 앱 없이 웹/PWA» 로 가는 반대 방향 검토 |

🔑 **2번과 3번이 실질적인 트리거다.** 둘 다 **«권한 요구 수준의 차이»** 라는 같은 축이다 — 일반 참가자에게 «항상 허용»을 요구하는 것이 정당한가.

⚠️ **이 판단은 실사용 데이터 없이 내려졌다.** 참가자 중 몇 %가 백그라운드 권한을 허용하는지 모른다. 첫 행사 후 **권한 허용률**을 보고 재검토할 것.
