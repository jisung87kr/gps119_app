# 05. 스토어 배포 (App Store · Play Store)

> 요구: **「appstore, playstore 모두 배포」**

## 1. 심사 리스크 — 이 앱의 고유한 두 가지

일반적인 체크리스트보다, **GPS119 이기 때문에 특히 위험한 것**을 먼저 다룬다.

### 1-1. 🔴 App Store 4.2 — 최소 기능 (웹사이트 래퍼)

[`01`](01-webview-strategy.md) 에서 택한 «원격 URL 로딩» 방식은 심사자 눈에 **"웹사이트를 앱으로 포장한 것"** 으로 보인다. 4.2 는 리젝 사유 상위권이다.

**방어 논리 (그리고 이게 이 에픽의 존재 이유와 같다):**

| 근거 | 설명 |
|---|---|
| **백그라운드 위치** | 화면이 꺼진 상태에서 참가자 위치를 추적한다. 웹으로 **불가능** |
| **푸시 알림** | 앱이 죽어 있어도 신고·지령을 전달한다. iOS 웹 푸시는 홈화면 추가가 전제라 실효성이 낮다 |
| **네이티브 권한 UX** | 위치 3단계 권한, 설정 앱 딥링크 |

심사 노트에 **한국어/영어로 «행사 현장 안전관제 앱이며, 백그라운드 위치와 푸시가 핵심 기능»** 임을 명시하고, **데모 계정 + 시연 영상**을 첨부한다.

⚠️ 데모 계정은 **전화번호 로그인**이라는 점을 심사자가 모른다. 별도 안내 필수(관리자는 이메일, 일반 사용자는 전화번호 — `FortifyServiceProvider`).

### 1-2. 🔴 위치 상시 수집의 정당화

두 스토어 모두 **백그라운드/상시 위치**에 별도 심사를 건다.

| 스토어 | 요구 |
|---|---|
| **App Store** | `NSLocationAlwaysAndWhenInUseUsageDescription` 에 **구체적 목적**. "더 나은 서비스를 위해" 같은 문구는 리젝. 백그라운드 모드 사용 사유 소명 |
| **Play Store** | **백그라운드 위치 권한 선언 양식** 별도 제출 — 기능 시연 영상, 왜 포그라운드로 불충분한지, 사용자 고지 화면 캡처 |

**작성 방향:** *"마라톤·등산 등 야외 행사에서 참가자가 사고를 당했을 때, 본인이 위치를 설명할 수 없는 상황에서 구조대가 정확한 지점으로 이동하기 위해 위치를 수집합니다. 행사 참여 중에만, 사용자가 위치 공유를 켠 동안에만 수집합니다."*

🔑 **«행사 참여 중에만»이 방어의 핵심이다.** `event_participants.status = active` 이고 `sharing_location = true` 일 때만 수집한다는 것을 **코드·화면·고지가 일치되게** 보여줘야 한다. 지금 `LocationService::record` 가 `sharing_location=false` 를 short-circuit 하는 것이 이 주장의 근거가 된다.

⚠️ 반대로 **`location_pings` 보존기간이 미정인 것은 약점**이다([`02`](02-location-accuracy.md) §6). 심사에서 «얼마나 보관하나»를 물으면 답이 없다. **N0 에서 정해야 한다.**

🔴 **다만 «짧을수록 좋다»가 아니다.** 위치정보법은 **제공사실 확인자료를 최소 6개월 보존**하도록 요구한다 — 궤적 원본은 파기 대상이지만 **«누구에게 언제 제공했는가»는 보존 의무 대상**이고, 지금 설계에 후자가 없다. 상세와 갈래는 [`02 §6-1`](02-location-accuracy.md) 참조. 심사 답변도 *"짧게 지웁니다"* 가 아니라 **«궤적은 N일 후 파기, 제공이력은 법정기간 보존»** 두 갈래로 준비해야 한다.

## 2. 제출 전 체크리스트

### 공통

- [ ] **개인정보처리방침 URL** — 위치·연락처·기기토큰 수집 항목이 실제와 일치
- [ ] 계정 **삭제 경로** (두 스토어 모두 필수). 웹에 `/profile/delete` 존재 — 앱에서 도달 가능한지 확인
- [ ] 아이콘·스플래시 — 🔴 **현재 `public/icon-192/512.png` 는 GD 로 생성한 플레이스홀더**(선행 에픽에 명시). 브랜드 자산 교체 필요
- [ ] 스크린샷 (기기 크기별)
- [ ] 연령 등급 — 위치 기반·사용자 간 정보 노출 고려
- [ ] 데모 계정 2종(참가자·상황실) + 시연용 활성 행사

### App Store

- [ ] `NSLocationWhenInUseUsageDescription` / `NSLocationAlwaysAndWhenInUseUsageDescription`
- [ ] `UIBackgroundModes: ["location", "remote-notification"]`
- [ ] **App Privacy «영양성분표»** — 위치(정밀), 연락처, 식별자. «추적(Tracking)» 해당 여부 판단
- [ ] APNs 인증키(.p8) — 명의 주체 확정 필요(M-8)

### Play Store

- [ ] `ACCESS_FINE_LOCATION` + `ACCESS_BACKGROUND_LOCATION` + `FOREGROUND_SERVICE_LOCATION` + `POST_NOTIFICATIONS`(13+)
- [ ] **백그라운드 위치 선언 양식** + 시연 영상
- [ ] **Data safety** 섹션
- [ ] **타깃 API 레벨 — `targetSdkVersion` 36 이상**(Android 16). 2026-08-31 부터 **신규 앱·업데이트 모두** 이 기준이고, N4 는 그 이후일 가능성이 높다. 기한 연장(2026-11-01)은 Play Console 신청 사항이지 기본값이 아니다. 매년 상향되므로 **제출 시점에 다시 확인**한다 → <https://developer.android.com/google/play/requirements/target-sdk>

### 한국 특수사항

- [ ] **위치정보사업자 / 위치기반서비스사업자 신고** — 🔴 **법무 확인 필요(M-15)**. 이건 스토어가 아니라 국내법 이슈이고, **이미 웹으로 운영 중이므로 앱 이전에 걸리는 문제**다
  - ⚠️ *"대상일 수 있다"* 로 적어뒀던 것을 **과소평가**로 정정한다(2026-08-05). GPS119 는 참가자의 개인위치정보를 수집해 **상황실·구급대라는 제3자에게 제공**하는 구조다 — 최소한 위치기반서비스사업 신고는 걸린다고 보고 준비하는 게 맞다. 법무에는 «대상인가»가 아니라 **«어느 유형으로, 언제까지»** 를 묻는다
  - [ ] 법무 질의에 **보존 의무 자료 범위**를 같이 넣을 것 → [`02 §6-1`](02-location-accuracy.md)
  - [ ] 8세 이하 아동 등의 **보호의무자 동의** 경로 — 마라톤·등산 행사에 아동 참가 가능성이 있다
- [ ] 위치정보 이용약관 별도 동의 (개인정보처리방침과 분리)

## 3. 명의 — 먼저 정해야 할 것

🔴 **스토어 계정·인증서·FCM 프로젝트의 명의 주체가 미정이다.**

이미 2026-07-22 시점에 «앱 출시 시 계정·사업자 명의 주체를 누구로 할 것인가»가 **미정 항목**으로 식별되어 있었고(대가 구조·운영비 부담·소스 IP 귀속과 함께 4건), *"출시 이후에는 되돌리기 어렵다"* 고 기록돼 있다. 2026-08-05 현재 **네 건 모두 여전히 미정**이다.

| 자산 | 이전 난이도 |
|---|---|
| Apple Developer 계정 (앱 소유권) | 이전 가능하나 절차 복잡 |
| Play Console 계정 | 앱 이전 가능(수수료·절차) |
| APNs 키 / FCM 프로젝트 | 재발급 시 **기존 기기 토큰 전부 무효** |
| 앱 서명 키 (Android) | 🔴 **분실·이전 실패 시 앱 업데이트 불가** |

🔑 **N0 의 블로커다.** 코드보다 먼저 정해야 한다.

## 4. 릴리스 운영

- **버전 정책**: 앱 셸은 `major.minor.patch`, 웹은 별도. 웹뷰 방식이라 **웹 배포가 앱 내용을 바꾸므로**, 앱 스토어 버전은 «네이티브 기능 변경»에만 올린다
- **강제 업데이트 경로**: 서버가 최소 지원 앱 버전을 내려주고, 미달이면 앱이 업데이트 안내를 띄운다. 네이티브 브리지 규약이 바뀔 때 필요
- **단계적 출시**: Play Store 단계별 출시(1%→100%) 활용. 백그라운드 위치는 기기 편차가 크다
- **크래시·에러 수집**: 웹뷰 안 JS 에러는 네이티브 크래시 리포터에 안 잡힌다. **웹 쪽 에러 수집을 따로 붙일지 결정 필요(M-16)**

## Universal Links / App Links (2026-09-01)

**QR 을 찍으면 브라우저가 아니라 앱이 열린다.** 이게 없으면 행사 현장에서 참가자가
입장 QR 을 찍는 순간 앱이 있어도 Safari 로 떨어지고, **백그라운드 위치도 푸시도 그
사람에게는 무의미해진다** — 앱을 만든 이유가 반감된다.

| 무엇 | 어디 |
|---|---|
| `apple-app-site-association` | 웹 `public/.well-known/` (확장자 없음) |
| `assetlinks.json` | 웹 `public/.well-known/` |
| `com.apple.developer.associated-domains` | 셸 `ios/App/App/App.entitlements` |
| `intent-filter android:autoVerify="true"` | 셸 `AndroidManifest.xml` |
| `ForceType application/json` | 웹 `docker/apache/common.conf` |

🔑 **실패가 조용하다.** OS 는 파일을 못 읽거나 지문이 안 맞으면 **그냥 브라우저로**
떨어뜨린다. 오류도 로그도 없어서, 「왜 앱이 안 열리지」로만 보인다.

### 🔴 밟기 쉬운 것 넷

**① AASA 는 확장자가 없다.** 그대로 두면 Content-Type 이 «비어» 나가고 iOS 가 무시한다.
Apple 은 `application/json` 을 요구한다 → Apache `ForceType`.

**② `appIDs` 는 「팀ID.번들ID」다.** 번들ID 만 적으면 조용히 무시된다.

**③ Play 로 배포하면 지문이 «달라진다».** Play 앱 서명이 업로드 키가 아닌 **구글 키로
다시 서명**하기 때문이다. 지금 `assetlinks.json` 에는 **업로드 키 지문만** 있다 —
사이드로드·내부 직접 설치에서는 되지만 **스토어 설치본에서는 안 된다.**
🔴 **첫 업로드 후 Play Console 의 앱 서명 키 지문을 «추가»할 것**(교체가 아니라 추가 —
내부 테스트용 사이드로드도 계속 쓴다).

**④ iOS 는 AASA 를 «설치 시점»에 가져가 캐시한다.** 서버 쪽을 고쳤으면 앱을 지웠다 다시
깔아야 반영된다. 안 그러면 「고쳤는데 그대로」가 된다.

### 확인 방법

```bash
# 파일이 제대로 나가는가
curl -sI https://gps119.co.kr/.well-known/apple-app-site-association | grep -i content-type
#   → application/json  (비어 있으면 ① 을 의심)

# 안드로이드가 실제로 검증했는가 (실기기)
adb shell pm get-app-links kr.co.gps119.app
#   → verified 가 아니면 지문 불일치(③)
```

⚠️ **`autoVerify` 는 「검증하겠다」는 선언일 뿐 보장이 아니다.** 설치 시 안드로이드가
`assetlinks.json` 을 가져가 대조하고, 실패하면 일반 링크로 떨어진다.
