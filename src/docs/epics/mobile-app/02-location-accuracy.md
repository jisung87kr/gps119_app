# 02. 위치 수집과 정확도

> 요구: **「사용자 위치정보 수집, 정확도 중요」**
> 이 문서의 결론: **웹 단계의 스로틀 결함은 고쳤다(§1). 앱에서 다시 실측해야 한다(§2).**

## 1. ✅ 스로틀 결함 — 발견과 수정 (2026-08-05 완료)

> 아래는 **이 에픽을 기획하며 발견해 고친 것**이다. 현재 코드에는 없는 문제이나,
> 같은 함정을 앱에서 반복하지 않기 위해 경위를 남긴다.

### 발견 당시의 사실

```php
// routes/api.php (수정 전)
// ping 수신: active 참가자(역할무관) + rate-limit(초당 1~2). 큐로 적재.  ← 주석이 틀렸다
Route::post('/events/{id}/location', [LocationApiController::class, 'store'])
    ->middleware(['event.member', 'throttle:2,1']);
```

Laravel 의 `throttle:maxAttempts,decayMinutes` 이므로 `throttle:2,1` 은 **분당 2회**다. 그런데 클라이언트는 이동 중 5초마다(분당 12회) 보내면서 주석에 *"백엔드 throttle(2/s)와 **정합**"* 이라고 적어놨다. **120배 어긋난 채 스스로 정합이라 믿고 있었다.**

실측(연속 호출):

```
0:422(limit 2) | 1:422(limit 2) | 2:429 | 3:429 | 4:429
응답 헤더: X-RateLimit-Limit: 2
```

(422 는 테스트 페이로드의 검증 실패로 **스로틀은 통과**했다는 뜻. 3번째부터 429.)

| 상태 | 클라이언트 전송 | 서버 통과 | 손실 |
|---|---|---|---|
| **이동 중** | 분당 12회 | 분당 2회 | 🔴 **10/12 (83%)** |
| 정지 | 분당 2회 | 분당 2회 | 0 |

🔑 **가장 정확도가 필요한 「이동 중」에 정확히 실패했다.** 실패 버퍼도 2개뿐이라 복구되지 않았다.

⚠️ **이 손실이 관제에서 「끊긴 마커」로 보이지 않았다** — `event_participants.last_lat/lng` 캐시가 마지막 성공 값을 유지하기 때문이다. **조용히 부정확해졌다.** 앱에서도 같은 은폐가 일어날 수 있으니, 전송 실패율을 화면 어딘가에 노출할지 검토할 것.

### 조치

| 항목 | 결과 |
|---|---|
| 스로틀 | `throttle:2,1` → **`throttle:30,1`** (이동 12회 + 재전송·복수탭 여유) |
| 클라이언트 | **429 백오프** 신설(20초 창) — 이전에는 429 를 일반 실패로 처리해 즉시 재시도하며 악화시켰다 |
| 실패 버퍼 | 2 → **12** (이동 1분치) |
| 주석 | `routes/api.php`·`locationShare.js` 두 곳 정정 + "값 변경 시 양쪽을 같이 보라" 경고 |
| 회귀 테스트 | PHP: 이동 시나리오(분당 12회)에서 429 = 0건 · **Vitest 12건** (백오프 진입·창 유지·복구·비429 구분) |

## 2. ⚠️ 앱에서 다시 정해야 하는 값

**`30/분` 은 «웹 기준» 추정치다.** 백그라운드 추적을 붙이면 전송량 특성이 달라진다.

- 포그라운드 서비스는 화면이 꺼져도 계속 보낸다 → 총량 증가
- 반대로 OS 가 위치 갱신 빈도를 조절(스로틀링)할 수 있다 → 불규칙해짐
- 여러 기기·재설치로 같은 사용자가 중복 전송할 여지

→ **N3 에서 실기기로 재실측하고 스로틀·백오프 값을 조정한다.** 지금 값을 그대로 들고 가지 말 것.

## 3. 웹뷰에서 위치를 어떻게 얻는가

### 3-1. 웹 `navigator.geolocation` 만으로는 부족하다

현재 `locationShare.js` 는 `watchPosition` + `enableHighAccuracy: true` 를 쓴다. 웹뷰 안에서도 동작하지만 **앱이 백그라운드로 가면 멈춘다.**

행사 현장 시나리오에서 이건 치명적이다 — 참가자는 폰을 주머니에 넣고 달리고, 구급대원은 지도 대신 통화 앱을 보고 있다. **화면이 꺼지면 위치가 끊기는 관제는 관제가 아니다.**

### 3-2. 네이티브 플러그인으로 대체

| 플랫폼 | 필요한 것 |
|---|---|
| **Android** | **Foreground Service** (`FOREGROUND_SERVICE_LOCATION`) + 상시 알림. Android 8+ 는 백그라운드 위치 취득 빈도가 제한되므로 포그라운드 서비스가 사실상 필수 |
| **iOS** | `UIBackgroundModes: ["location"]` + `allowsBackgroundLocationUpdates` + **파란 상태바 인디케이터** |

Capacitor 생태계에서는 `@capacitor/geolocation` 이 **백그라운드를 지원하지 않는다.** 백그라운드 지오로케이션 전용 커뮤니티 플러그인이 필요하다.

#### ✅ M-4 해소 (2026-08-31) — `@capacitor-community/background-geolocation`

「유지보수·라이선스·양 OS 를 반드시 실측하라」는 요구대로 **버릴 브랜치에서 실제로 붙여 빌드했다.** 후보는 둘이었다.

| | `@capacitor-community/…` | `@transistorsoft/…` |
|---|---|---|
| 라이선스 | **MIT** | CUSTOM — 릴리스 빌드는 **유료 구매** |
| Capacitor peer | `>=3.0.0` | `^8.0.0` |
| 최근 릴리스 | `1.2.26` · **2025-08-28 (1년 전)** | `9.4.0` · 2026-08-30 |

⚠️ npm 의 `time.modified` 는 커뮤니티 쪽이 2026-01 로 찍힌다. **메타데이터만 건드린 것**이고 실제 배포는 2025-08 이 마지막이다 — 그 필드만 보면 「최근까지 관리된다」로 **오독한다.**

**실측 결과 (Capacitor 8.5.0):**

| 관문 | 결과 |
|---|---|
| Android `assembleDebug` | ✅ `BUILD SUCCESSFUL` |
| iOS `xcodebuild` | ✅ `** BUILD SUCCEEDED **` (`exit=0`) |
| SPM 해석 | ✅ `capacitor-swift-pm @ 8.5.0` |
| **실제 링크** | ✅ `App.debug.dylib` 에 심볼 165개 (`addWatcher` 등). 대조군 `AppDelegate` 97개 |

🔑 **「빌드 성공」에서 멈추면 안 된다.** 플러그인이 링크에서 조용히 빠져도 빌드는 통과한다.
바이너리까지 봐야 한다 — 그리고 **`App.app/App` 이 아니라 `App.app/App.debug.dylib` 을 본다.**
Xcode 16+ 에서 앞엣것은 92KB 껍데기라 우리 `AppDelegate` 조차 안 나온다(대조군을 같이 세면
방법이 틀린 걸 바로 안다).

**무료를 고른 근거 — 「1년째 공백」은 오늘의 결함이 아니라 내일의 위험이고, 그 위험은
아래 §3-3 브리지가 이미 흡수한다.** 플러그인은 `bridge.js` 뒤에만 있으므로 나중에 깨지면
브리지 안쪽만 갈아끼우면 되고 전송 정책·권한 UX 는 안 흔들린다. **지금 돈을 쓸 근거가
실측으로는 없다.** 유료 쪽은 스파이크하지 않았다 — `^8.0.0` 을 선언하니 빌드는 당연히 되고,
확인해도 「예상대로」밖에 안 나온다.

⚠️ **되돌릴 조건을 미리 적어 둔다.** Android 16 / iOS 27 대응이 필요해졌는데 업스트림이
여전히 멈춰 있으면 그때 유료로 간다. 그 판단을 「불편해서」가 아니라 **「OS 가 요구하는데
업스트림이 안 따라온다」** 로 한다.

### 3-3. 브리지 설계 — ✅ 구현됨 (2026-08-31)

웹 코드가 Capacitor 를 직접 알지 않게 어댑터를 둔다. `locationShare.js` 는
**전송 정책(적응형 주기·버퍼·429 백오프)만 담당**하고 위치 «취득»은 위임한다.
이렇게 나눠야 셸을 바꿔도 전송 로직이 안 흔들린다.

```
resources/js/native/bridge.js           «그 앱이 이 기능을 아는가» 판정
  ├─ isNativeApp() · nativePlatform()
  └─ hasNativeCapability(BACKGROUND_LOCATION)

resources/js/native/locationTracker.js  «어떻게 얻는가» — 네이티브 어댑터
  ├─ createNativeLocationTracker(env) → 트래커 | null
  └─ toLocationPermission(raw)        → M-5 값으로 접기 (경계 매핑)

resources/js/app.js                     window.__gps119Bridge.locationTracker
public/js/components/locationShare.js   config.tracker 주입, 없으면 웹 경로
```

⚠️ **애초 설계는 `startLocationTracking()` 을 `bridge.js` «안»에 두는 것이었으나
파일을 나눴다.** `bridge.js` 는 「그 앱이 이 기능을 아는가」를 판정하는 곳이고, 거기에
플러그인 세부(`addWatcher` 옵션·payload 변환)를 섞으면 **협상 로직이 묻힌다.**
갈아끼울 때 봐야 할 곳도 흐려진다.

🔑 **웹 트래커는 브리지 쪽에 «없다».** `createNativeLocationTracker()` 는 네이티브가
가능할 때만 트래커를 주고 아니면 `null` 이다 — 웹 구현은 `locationShare.js` 안에 이미
있으므로 여기에 또 만들면 **0-8(같은 로직 두 벌 → 드리프트)이 반복된다.**

🔴 **`null` 을 주는 조건이 그 함수의 절반이다.** 웹이거나 · 플러그인이 없거나(구버전
셸) · 기능은 있다는데 `Capacitor.Plugins` 에 없으면 `null`. 여기서 잘못 트래커를 주면
**구버전 앱이 없는 플러그인을 부르다 깨진다.** 「앱이면 네이티브」가 아니라 「그 앱이
그 기능을 아는가」다.

📌 **`window` 를 거치는 이유.** `public/js/components/*` 는 브라우저에 그대로 서빙되는
모듈이고 Vite 는 번들에서 `public/` 의 JS import 를 막는다(`vitest.config.js` 주석 참조).
`import` 로 이을 수 없어서 **한 지점에서만** `window` 로 건네고, 받는 쪽은 «주입»으로
취급한다. 그래서 `locationShare.js` 는 Capacitor 를 영영 모른다.

📌 플러그인 payload 는 **W3C `GeolocationPosition` «모양»으로 바꿔** 넘긴다. 그게 이미
안쪽 계약이라 웹 경로는 무변환이고 적응은 네이티브에서만 일어난다. 권한 오류도
`err.code === err.PERMISSION_DENIED` 계약에 맞춰 접는다 — 안 그러면 권한 거부가
「알 수 없는 오류」로 표시된다.

🔑 **이 구조가 M-4 를 되돌릴 수 있게 하는 실체다.** [ADR-0008](../../adr/0008-location-permission-as-separate-axis.md)
와 §3-2 에 적은 되돌릴 조건이 실제로 오면, 갈아끼울 곳은 `locationTracker.js` 와
`bridge.js` 의 플러그인 이름 문자열 **둘뿐**이다.

⚠️ **네이티브 경로는 실기기 미검증이다.** 셸에 플러그인이 아직 없어 판정이 항상 false 이고
**지금은 언제나 웹 경로로 돈다.** 테스트(Vitest 22건)는 가짜 Capacitor 로 «계약»만
고정한 것이다 — 플러그인 배선은 셸 저장소 몫이고 N3 에 남는다.

## 4. 권한 — 3단계로 나눠 요청한다

한 번에 «항상 허용»을 요구하면 거절률이 급등한다. 순서:

| 단계 | 시점 | 요청 |
|---|---|---|
| 1 | 행사 입장 직후 | **사용 중에만 허용** (`WhenInUse`) |
| 2 | 위치공유 토글 ON 또는 첫 백그라운드 필요 시점 | **항상 허용** — «왜 필요한지»를 앱 자체 화면으로 먼저 설명한 뒤 OS 다이얼로그 |
| 3 | 거부 시 | 기능 제한 안내 + 설정 앱 딥링크 |

**iOS 는 «항상 허용»을 OS 가 나중에 다시 물어본다**(재확인 프롬프트). 여기서 사용자가 «사용 중»으로 되돌리는 것을 감지해 관제에 «백그라운드 추적 불가» 상태로 표시해야 한다. 안 그러면 상황실이 «보이고 있다」고 착각한다.

🔴 **`event_participants.sharing_location` 은 앱 권한 상태와 별개다.** **«공유 켬 + OS 권한 없음»** 상태를 구분해 표현해야 한다.

#### ✅ M-5 해소 (2026-08-31) — 권한을 별도 축으로, 상태는 서버에서 파생 → [ADR-0008](../../adr/0008-location-permission-as-separate-axis.md)

관제가 알아야 할 것은 셋인데 둘밖에 없었다.

| 축 | 질문 | 이전 |
|---|---|---|
| 의도 | 사용자가 켰는가 | `sharing_location` — **있지만 관제로 안 내려갔다** |
| 능력 | OS 가 허락했는가 | 🔴 **없음** |
| 증거 | 실제로 들어오는가 | `last_seen_at` → `online` |

그래서 「껐다」·「권한이 없다」·「네트워크가 끊겼다」가 전부 같은 «오프라인»으로 보였다.
**포그라운드 공유에서는 「화면 보고 있으니 곧 돌아오겠지」로 넘어갔지만, 배경 추적은
«안 보고 있어도 보인다»가 전제라 그 가정이 무너진다.**

서버 구현이 끝났다 — `location_permission` 컬럼, `LocationPermission`/`TrackingState` enum,
`PATCH /api/events/{id}/location-permission`, roster 의 `tracking_state`. 테스트 15건.

⚠️ **셸의 보고 배선은 N3 몫이다.** 앱이 보고하지 않으면 전원 `unknown`/`off` 로 남는다 —
서버만 배포해서는 화면이 달라지지 않는다. 관제 UI 배지도 아직이다.

🔴 **`unknown` 은 「문제 없음」이 아니라 「모름」이다.** 웹 사용자가 다수인 동안은 관제
화면 대부분이 `unknown` 이다. 이걸 정상처럼 칠하면 M-5 를 다시 잃는다.

## 5. 정확도 설계

| 항목 | 값 | 근거 |
|---|---|---|
| `enableHighAccuracy` | true (유지) | 산길·코스에서 네트워크 측위로는 부족 |
| 이동 판정 | 10m (`MOVE_THRESHOLD_M`, 유지) | |
| 이동 중 전송 | 5초 (유지 — 서버 스로틀 상향으로 실효화됨) | |
| 정지 하트비트 | 30초 (유지) | |
| **정확도(accuracy)** | ✅ 수집→저장→**화면**까지 연결 완료 (아래) | 정확도 100m 짜리 픽스를 10m 짜리와 같이 그리면 관제가 틀린 확신을 갖는다 |
| **배터리** | 포그라운드 서비스 상시 = 배터리 소모 큼 | 행사 시간(수 시간) 기준으로 실측 필요 |

| **관제 roster 응답** | 🔴 없음 | ✅ `rosterForControl` 에 포함 |
| **관제 화면 표시** | 🔴 사용처 0건 | ✅ 마커 인포윈도에 오차 반경 |

🔑 **끊긴 지점이 「최초 로드」였다.** 브로드캐스트에는 accuracy 가 실려 있었지만 캐시에 없어서 **관제가 처음 켜질 때 받는 roster 에는 빠져 있었고**, SPA 는 실시간으로 들어온 값도 쓰지 않고 버렸다. 결과적으로 오차 5m 인 사람과 500m 인 사람이 «똑같은 점»으로 찍혔다. 산에서 500m 는 사람을 못 찾는 거리다.

**표시 규칙** (`markerPool.js`):

| 오차 | 표기 |
|---|---|
| < 50m | 초록 `오차 반경 ±12m` |
| 50~150m | 주황 |
| ≥ 150m | 빨강 `오차 반경 ±300m · 신뢰 낮음` |
| 값 없음 | 회색 **`정확도 정보 없음`** — 빈칸으로 두면 «정확하다»로 읽힌다 |

> 남은 것: 지도에 **오차 반경 원(circle)** 표시는 넣지 않았다. 마커 수가 많을 때 렌더 비용을 재보고 결정한다.

## 6. 개인정보 — 앱은 요구 수준을 올린다

- 🔴 **`location_pings` 자동 파기 정책이 아직 없다**(선행 에픽 Q2/OI-7 미결). **백그라운드 상시 수집이 붙으면 데이터량과 민감도가 동시에 올라간다.** 스토어 심사에서도 보관 기간을 묻는다
- 두 스토어 모두 **위치 데이터 수집·목적·제3자 제공 여부 신고**가 필수 → [`05-store-release.md`](05-store-release.md)
- 앱 내 **위치 이력 조회·삭제 요청 경로**를 제공할 것인지 결정 필요(M-6)

### 🔴 6-1. 「파기」로만 접근하면 틀린다 — 법이 «남기라»는 것이 따로 있다 (2026-08-05 검토)

지금까지 이 항목은 **«보존기간을 정하고 지운다»** 로만 프레이밍돼 있었고, [`05 §1-2`](05-store-release.md) 도 짧은 보관을 심사 방어 논리로 봤다. **그 방향만으로는 위험하다.**

「위치정보의 보호 및 이용 등에 관한 법률」은 위치정보사업자등에게 **위치정보 수집·이용·제공 «사실 확인자료»를 위치정보시스템에 자동 기록·보존할 의무**를 지우고, 시행령이 **최소 보관기간(6개월)** 을 둔다. 즉 **파기 잡을 짜기 전에 두 가지를 갈라야 한다.**

| 구분 | 무엇 | 방향 |
|---|---|---|
| **궤적 원본** | `location_pings` 의 좌표·정확도 시계열 | **파기 대상.** 보존기간을 짧게 정하는 게 맞다 |
| **제공사실 확인자료** | «누구의 위치를, 언제, 누구에게 제공했는가»의 기록 | 🔴 **보존 의무 대상.** 지우면 안 된다 |

⚠️ **지금 설계에는 후자가 아예 없다.** `location_pings` 에 **위치를 기록한 시각(`recorded_at`)은 있다** — 없는 것은 Laravel `created_at`/`updated_at` 뿐이다([마이그레이션](../../../database/migrations/2026_06_26_100001_create_location_pings_table.php)). 문제는 시각이 아니라 **«누구에게 제공했는가»** 다: 관제·구급대에게 브로드캐스트한 «제공 사실»을 남기는 테이블이 따로 없다. **0-3 을 지금 문서대로 실행하면 «법이 남기라는 것까지 지우는 파기 잡»이 나온다.**

🔑 **M-15(법무 확인)에 이걸 같이 물어야 한다** — 「신고 대상인가」만이 아니라 **「우리가 남겨야 하는 자료가 무엇인가」**. 답에 따라 M-6 의 산출물이 «파기 잡 하나»가 아니라 **«파기 잡 + 제공이력 테이블»** 두 개가 된다.
