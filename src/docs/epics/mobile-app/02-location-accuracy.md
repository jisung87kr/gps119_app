# 02. 위치 수집과 정확도

> 요구: **「사용자 위치정보 수집, 정확도 중요」**
> 이 문서의 결론: **앱을 얹기 전에 서버 스로틀부터 고쳐야 한다. 지금은 「이동 중」에 정확히 실패한다.**

## 1. 🔴 현재 결함 — 분당 2회 스로틀

### 사실

```php
// routes/api.php:34-36
// ping 수신: active 참가자(역할무관) + rate-limit(초당 1~2). 큐로 적재.
Route::post('/events/{id}/location', [LocationApiController::class, 'store'])
    ->middleware(['event.member', 'throttle:2,1']);
```

Laravel 의 `throttle:maxAttempts,decayMinutes` 이므로 **`throttle:2,1` = 분당 2회**다. 주석은 "초당 1~2"라고 적혀 있다.

클라이언트는 이렇게 보낸다.

```js
// public/js/components/locationShare.js:9,14-15
//   백엔드 throttle(2/s)·sharing-off 스킵과 정합.        ← 2/s 라고 «믿고» 있다
const MOVE_INTERVAL_MS = 5000;       // 이동 중 = 분당 12회
const STATIONARY_INTERVAL_MS = 30000; // 정지 중 = 분당 2회
```

### 실측 (2026-08-05)

로그인 세션에서 `POST /api/events/7/location` 을 연속 호출:

```
0:422(limit 2) | 1:422(limit 2) | 2:429 | 3:429 | 4:429
응답 헤더: X-RateLimit-Limit: 2
```

(422 는 테스트 페이로드의 검증 실패로 **스로틀은 통과**했다는 뜻. 3번째부터 429.)

### 결과

| 상태 | 클라이언트 전송 | 서버 통과 | 손실 |
|---|---|---|---|
| **이동 중** | 분당 12회 | 분당 2회 | 🔴 **10/12 (83%)** |
| 정지 | 분당 2회 | 분당 2회 | 0 |

🔑 **가장 정확도가 필요한 「이동 중」에 정확히 실패한다.** 그리고 실패 버퍼가 `MAX_BUFFER = 2` 라서(`locationShare.js:16`) 재전송으로도 복구되지 않는다.

⚠️ 관제 화면에서 이 손실이 «끊긴 마커»로 보이지 않는 이유는, `event_participants.last_lat/lng` 캐시가 마지막 성공 값을 유지하기 때문이다. **조용히 부정확해진다.**

## 2. 고칠 것 (N0 — 앱 착수 전)

```php
// 이동 중 5초 간격(분당 12회) + 여유. 참가자별 제한이므로 사용자 단위로 건다.
->middleware(['event.member', 'throttle:30,1'])
```

- `30/분` 은 이동 5초 간격(12) 에 재전송·복수 탭 여유를 얹은 값이다. 실측 후 조정
- **주석 3곳을 동시에 정정한다** — `routes/api.php:34`, `locationShare.js:9`, 관련 에픽 문서
- 클라이언트에 **429 백오프**를 넣는다. 지금은 429 를 일반 실패로 처리해 버퍼(2개)에만 담고 버린다
- 회귀 테스트: *이동 시나리오(분당 12회 전송)에서 429 가 0건* 을 고정

> 🔴 **백그라운드 추적을 붙이면 전송량이 오히려 늘어난다.** 이 순서를 지키지 않으면 앱이 문제를 키운다.

## 3. 웹뷰에서 위치를 어떻게 얻는가

### 3-1. 웹 `navigator.geolocation` 만으로는 부족하다

현재 `locationShare.js` 는 `watchPosition` + `enableHighAccuracy: true` 를 쓴다. 웹뷰 안에서도 동작하지만 **앱이 백그라운드로 가면 멈춘다.**

행사 현장 시나리오에서 이건 치명적이다 — 참가자는 폰을 주머니에 넣고 달리고, 구급대원은 지도 대신 통화 앱을 보고 있다. **화면이 꺼지면 위치가 끊기는 관제는 관제가 아니다.**

### 3-2. 네이티브 플러그인으로 대체

| 플랫폼 | 필요한 것 |
|---|---|
| **Android** | **Foreground Service** (`FOREGROUND_SERVICE_LOCATION`) + 상시 알림. Android 8+ 는 백그라운드 위치 취득 빈도가 제한되므로 포그라운드 서비스가 사실상 필수 |
| **iOS** | `UIBackgroundModes: ["location"]` + `allowsBackgroundLocationUpdates` + **파란 상태바 인디케이터** |

Capacitor 생태계에서는 `@capacitor/geolocation` 이 **백그라운드를 지원하지 않는다.** 백그라운드 지오로케이션 전용 커뮤니티 플러그인이 필요하다 → **플러그인 선정이 미결(M-4)**. 유지보수 상태·라이선스·두 OS 지원 여부를 반드시 실측할 것.

### 3-3. 브리지 설계

웹 코드가 Capacitor 를 직접 알지 않게 어댑터를 하나 둔다.

```
resources/js/native/bridge.js
  ├─ isNativeApp()          → window.Capacitor 존재 여부
  ├─ startLocationTracking(opts, onFix)
  │     앱: 네이티브 플러그인 · 웹: 기존 watchPosition
  └─ stopLocationTracking()
```

`locationShare.js` 는 **전송 정책(적응형 주기·버퍼·429 백오프)만 담당**하고 위치 «취득»은 브리지에 위임한다. 이렇게 나눠야 셸을 바꿔도 전송 로직이 안 흔들린다.

## 4. 권한 — 3단계로 나눠 요청한다

한 번에 «항상 허용»을 요구하면 거절률이 급등한다. 순서:

| 단계 | 시점 | 요청 |
|---|---|---|
| 1 | 행사 입장 직후 | **사용 중에만 허용** (`WhenInUse`) |
| 2 | 위치공유 토글 ON 또는 첫 백그라운드 필요 시점 | **항상 허용** — «왜 필요한지»를 앱 자체 화면으로 먼저 설명한 뒤 OS 다이얼로그 |
| 3 | 거부 시 | 기능 제한 안내 + 설정 앱 딥링크 |

**iOS 는 «항상 허용»을 OS 가 나중에 다시 물어본다**(재확인 프롬프트). 여기서 사용자가 «사용 중»으로 되돌리는 것을 감지해 관제에 «백그라운드 추적 불가» 상태로 표시해야 한다. 안 그러면 상황실이 «보이고 있다」고 착각한다.

🔴 **`event_participants.sharing_location` 은 앱 권한 상태와 별개다.** 지금 코드는 이 플래그만 보고 있다. **«공유 켬 + OS 권한 없음»** 상태를 구분해 표현해야 한다 → 데이터 모델 변경 필요(M-5).

## 5. 정확도 설계

| 항목 | 값 | 근거 |
|---|---|---|
| `enableHighAccuracy` | true (유지) | 산길·코스에서 네트워크 측위로는 부족 |
| 이동 판정 | 10m (`MOVE_THRESHOLD_M`, 유지) | |
| 이동 중 전송 | 5초 (유지, 서버 스로틀 상향 후 실효) | |
| 정지 하트비트 | 30초 (유지) | |
| **정확도(accuracy)** | 수집·저장은 되는데 **화면까지 오지 않는다** (아래) | 정확도 100m 짜리 픽스를 10m 짜리와 같이 그리면 관제가 틀린 확신을 갖는다 |
| **배터리** | 포그라운드 서비스 상시 = 배터리 소모 큼 | 행사 시간(수 시간) 기준으로 실측 필요 |

### ✅ accuracy 파이프라인 — 2026-08-05 수정 완료

발견 당시 파이프라인이 **두 칸에서 끊겨 있었다.**

| 구간 | 발견 시 | 현재 |
|---|---|---|
| 클라이언트 전송 | ✅ `locationShare.js:125` | ✅ |
| 요청 검증 | ✅ `StoreLocationPingRequest.php:25` | ✅ |
| 이력 적재 | ✅ `location_pings.accuracy` | ✅ |
| 브로드캐스트 페이로드 | ✅ `ParticipantLocationUpdated` (원래 있었음) | ✅ |
| **참가자 캐시** | 🔴 없음 | ✅ `event_participants.last_accuracy` 추가 |
| **관제 roster 응답** | 🔴 없음 | ✅ `rosterForControl` 에 포함 |
| **관제 화면 표시** | 🔴 사용처 0건 | ✅ 마커 인포윈도에 오차 반경 |

🔑 **끊긴 지점이 「최초 로드」였다.** 브로드캐스트에는 accuracy 가 실려 있었지만 캐시에 없어서 **관제가 처음 켜질 때 받는 roster 에는 빠져 있었고**, SPA 는 실시간으로 들어온 값도 쓰지 않고 버렸다. 결과적으로 오차 5m 인 사람과 500m 인 사람이 «똑같은 점»으로 찍혔다. 산에서 500m 는 사람을 못 찾는 거리다.

**표시 규칙** (`markerPool.js`):

| 오차 | 표기 |
|---|---|
| < 50m | 초록 `오차 반경 ±12m` |
| 50~150m | 주황 |
| ≥ 150m | 빨강 `오차 반경 ±300m · 신뢰 낮음` |
| 값 없음 | 회색 **`정확도 정보 없음`** — 빈칸으로 두면 «정확하다»로 읽힌다 |

> 남은 것: 지도에 **오차 반경 원(circle)** 표시는 넣지 않았다. 마커 수가 많을 때 렌더 비용을 재보고 결정한다.

## 6. 개인정보 — 앱은 요구 수준을 올린다

- 🔴 **`location_pings` 자동 파기 정책이 아직 없다**(선행 에픽 Q2/OI-7 미결). **백그라운드 상시 수집이 붙으면 데이터량과 민감도가 동시에 올라간다.** 스토어 심사에서도 보관 기간을 묻는다
- 두 스토어 모두 **위치 데이터 수집·목적·제3자 제공 여부 신고**가 필수 → [`05-store-release.md`](05-store-release.md)
- 앱 내 **위치 이력 조회·삭제 요청 경로**를 제공할 것인지 결정 필요(M-6)
