# 07. 로드맵

## 마일스톤

### 🔴 N0 — 선행 정리 (앱 코드 착수 «전»)

앱을 얹기 전에 고쳐야 하는 것들. **N0 없이 N1 을 시작하면 앱이 기존 결함을 키운다.**

| # | 작업 | 근거 | 산출물 |
|---|---|---|---|
| 0-1 | **위치 스로틀 수정** `throttle:2,1` → `throttle:30,1` | 이동 중 핑 83% 가 429 로 버려짐(실측) | `routes/api.php`, 주석 3곳 정정, 회귀 테스트 |
| 0-2 | 클라이언트 **429 백오프** + 실패 버퍼 상향 | 지금은 429 를 일반 실패로 처리하고 버림 | `locationShare.js` |
| 0-3 | **`location_pings` 보존기간·자동파기 정책 확정** | 스토어 심사 질의 항목 · 백그라운드 수집으로 민감도 상승 | 정책 문서 + 파기 잡 |
| 0-4 | **스토어·인증서·FCM 명의 주체 확정** | 출시 후 되돌리기 어려움 | 합의 기록 |
| 0-5 | 운영 도메인 확정 + `SANCTUM_STATEFUL_DOMAINS` 검증 | 웹뷰 인증의 전제 | `.env` 확인 |
| 0-6 | 위치정보사업 신고 대상 여부 법무 확인 | 국내법. 앱 이전에 웹에도 해당 | 법무 회신 |

> 0-1·0-2 는 **모바일과 무관하게 지금 사용자에게 영향을 주고 있다.** 앱 계획과 별개로 즉시 처리 가치가 있다.

### N1 — 서버: 푸시 발송 계층

앱 없이도 웹 푸시로 검증 가능한 단위.

- `device_tokens` 테이블 + 등록/해제 API
- `PushService` (FCM HTTP v1, 무효 토큰 정리)
- `NotifyRescuers` 의 TODO 스텁 → `PushService` 연결
- 알림 종류 정의 + 페이로드에 **연락처 미포함**(ADR-0004 준수)
- (선택) 웹 푸시 VAPID — 상황실이 PC 를 쓰므로 실익이 클 수 있음

### N2 — 앱 셸 (최소 동작)

- `gps119_app_mobile` 레포 생성, Capacitor + 원격 URL
- 오프라인 폴백 화면, 아이콘·스플래시(**플레이스홀더 교체**)
- 웹 쪽 `bridge.js` + 앱 모드 감지 + SW 등록 스킵
- **검증 기준: 앱에서 로그인 → 신고 → 관제 실시간 수신이 웹과 동일하게 동작**
  (= 세션 쿠키·`/broadcasting/auth` 가 살아 있는지 확인 — [01](01-webview-strategy.md) 의 핵심 가설 검증)

### N3 — 네이티브 기능

- 푸시 SDK 연동 + 토큰 등록 + **딥링크 착지**(`?request=` 규약 재사용)
- 백그라운드 위치 플러그인 + 포그라운드 서비스(Android) / `UIBackgroundModes`(iOS)
- 권한 3단계 UX + **「공유 켬 + OS 권한 없음」 상태 표현**
- 정확도(accuracy) 저장 및 관제 노출
- 배터리 실측 (행사 4시간 기준)

### N4 — 스토어 배포

- 개인정보처리방침·위치 이용약관 정비
- App Privacy / Data safety 신고
- Play 백그라운드 위치 선언 양식 + 시연 영상
- 심사 노트(4.2 방어) + 데모 계정 2종
- TestFlight / 내부테스트 → 단계적 출시

## 검증 게이트

각 마일스톤의 통과 기준. **«구현했다»가 아니라 «작동을 봤다»로 판정한다.**

| 게이트 | 기준 |
|---|---|
| N0 | 이동 시나리오(분당 12회 전송)에서 **429 = 0건**. 회귀 테스트로 고정 |
| N2 | 실기기에서 로그인·신고·실시간 수신 성공. **에뮬레이터로는 판정하지 않는다** |
| N3 | **화면 끈 상태로 10분 이동 후, 관제 지도에 궤적이 끊김 없이 남는가** (양 OS) |
| N3 | 앱 강제 종료 상태에서 신규 신고 푸시 수신 → 탭 → 해당 신고 화면 착지 |
| N4 | 두 스토어 심사 통과 |

## 이 에픽의 최대 리스크

| 리스크 | 완화 |
|---|---|
| 🔴 **App Store 4.2 리젝** — 원격 URL 방식의 구조적 약점 | 네이티브 기능을 실제로 쓰고 심사 노트로 소명. 실패 시 로컬 번들 + 토큰 인증(B안)으로 전환 — **비용이 크므로 M-2 를 미리 정해둘 것** |
| 🔴 **백그라운드 위치가 기기별로 다르게 동작** | 실기기 매트릭스 검증. 제조사별 배터리 최적화(삼성·샤오미 등)가 서비스를 죽인다 |
| 🔴 **명의 미정으로 출시 후 이전 불가** | N0-4 에서 선행 확정 |
| ⚠️ 웹 배포가 구버전 앱을 깨뜨림 | 런타임 기능 협상(`getNativeCapabilities`) + 최소 지원 버전 |
| ⚠️ 푸시 없이 앱만 나감 | N1 을 N2 보다 먼저 두는 이유. **푸시 없는 모바일 관제는 안전 자산이 아니라 안전 부채** |
