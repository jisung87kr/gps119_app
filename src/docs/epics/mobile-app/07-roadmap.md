### N1 — 서버: 푸시 발송 계층

**웹 푸시(VAPID)를 같이 넣어 앱 없이 검증 가능한 단위로 만든다.**

- `device_tokens` 테이블 + 등록/해제 API
- `PushService` (FCM HTTP v1, 무효 토큰 정리)
- `NotifyRescuers` 의 TODO 스텁 → `PushService` 연결
- 알림 종류 정의 + 페이로드에 **연락처 미포함**(ADR-0004 준수)
- 🔴 **`/control` 의 `?project=` 딥링크 지원** — 지금은 `/admin/control` 만 처리해서 **행사 상황실에게 딥링크가 동작하지 않는다** → [`03 §5-1`](03-push-notifications.md)
- 웹 푸시 VAPID — ~~(선택)~~ **필수로 승격.** 아래 참조

> ⚠️ **VAPID 를 필수로 올린 이유(2026-08-05 검토)** — 원래 *"앱 없이도 웹 푸시로 검증 가능한 단위"* 라 써놓고 정작 웹 푸시를 «(선택)» 으로 뒀다. 선택이면 **N1 은 실기기 없이 검증할 방법이 없고**, N2 를 기다려야 하므로 "N1 을 N2 보다 먼저 둔다"는 순서 자체가 무의미해진다. 게다가 상황실은 PC 웹을 쓰므로([`04 §3-3`](04-app-partitioning.md)) **웹 푸시가 앱 푸시보다 먼저 필요하다.**

## 검증 게이트

각 마일스톤의 통과 기준. **«구현했다»가 아니라 «작동을 봤다»로 판정한다.**

| 게이트 | 기준 |
|---|---|
| N0 | 이동 시나리오(분당 12회 전송)에서 **429 = 0건**. 회귀 테스트로 고정 |
| N0 | **색상 미러 7/7 일치** — 값 비교를 자동 판정(테스트)으로 남긴다. 사람 눈으로 맞춘 건 또 어긋난다(0-8) |
| N1 | **행사를 2개 이상 맡은 상황실** 계정으로 `/control?project=B&request=N` 진입 → **B 행사의 N 배정 화면**이 열린다. 1개짜리 계정으로는 판정하지 않는다(우연히 통과한다) |
| N2 | 실기기에서 로그인·신고·실시간 수신 성공. **에뮬레이터로는 판정하지 않는다** |
| N3 | **화면 끈 상태로 10분 이동 후, 관제 지도에 궤적이 끊김 없이 남는가** (양 OS) |
| N3 | 앱 강제 종료 상태에서 신규 신고 푸시 수신 → 탭 → 해당 신고 화면 착지 |

### M-12 를 왜 N0 로 올렸나 (2026-08-05 리뷰 반영)

원래 N3(네이티브 기능 구현)에 두었는데, **너무 늦다.** 이 답에 두 가지가 걸려 있다.

- **앱 분리 판단(N2)** — [`04 §5`](04-app-partitioning.md) 의 재검토 트리거 2·3 이 전부 «권한 요구 수준의 차이»라는 같은 축이다. 참가자에게도 「항상 허용」을 요구한다면 분리 압력이 커진다
- **스토어 제출물(N4)** — Play 백그라운드 위치 선언 양식과 iOS 목적 문자열이 «누구에게 무엇을 요구하는가»를 그대로 서술해야 한다

🔑 **다만 «확정»은 N0 에서 못 한다** — 참가자 권한 허용률이라는 실사용 데이터가 없기 때문이다. 그래서 둘로 쪼갠다.

| 단계 | 무엇 |
|---|---|
| **N0** | **잠정 방침 한 줄.** 권장 기본값: *"참가자·운영진 = 사용 중만 / 구급대·상황실 = 항상 허용"*. 근거 — 일반 참가자에게 상시 위치를 요구하면 설치율과 심사 통과율이 동시에 나빠진다 |
| **N3** | 실기기에서 **권한 허용률 관측** 후 확정. 참가자 허용률이 충분히 높고 현장에서 필요가 확인되면 상향 |
