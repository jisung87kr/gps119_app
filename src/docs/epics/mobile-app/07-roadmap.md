> ⚠️ **1-0 을 먼저 한 이유** — 지금은 화면 한 칸이 틀리는 정도인 결함이 **푸시가 붙는 순간 전부 「폰이 잘못 울린다」로 승격**된다. 롤백된 지령이 브로드캐스트되면 「구급대원 폰이 울렸는데 지령이 없다」가 되고, 디스코드 실패로 잡이 재시도되면 「같은 신고로 폰이 두 번 운다」가 된다. 모델 훅 발행은 **팩토리로 행 하나만 만들어도 발송을 시도**하게 만든다.

> ⚠️ **VAPID 를 필수로 올린 이유(2026-08-05 검토)** — 원래 *"앱 없이도 웹 푸시로 검증 가능한 단위"* 라 써놓고 정작 웹 푸시를 «(선택)» 으로 뒀다. 선택이면 **N1 은 실기기 없이 검증할 방법이 없고**, N2 를 기다려야 하므로 "N1 을 N2 보다 먼저 둔다"는 순서 자체가 무의미해진다. 게다가 상황실은 PC 웹을 쓰므로([`04 §3-3`](04-app-partitioning.md)) **웹 푸시가 앱 푸시보다 먼저 필요하다.** → 실제로 그렇게 갔고, 덕분에 N2 없이 서버 경로를 끝까지 실측했다.

##### ⚠️ 실기기에서만 나오는 함정 3종

셋 다 **「서버 접근 로그에 아무것도 안 찍힌다」**는 같은 증상으로 나타난다. 그래서
네트워크·인증서 문제로 오진하기 쉽다. **제일 먼저 「앱이 어느 주소를 보고 있는가」를 본다.**

| # | 함정 | 확인 |
|---|---|---|
| 1 | **`npx cap run` 이 `server.url` 을 기본값으로 덮어쓴다.** 내부에서 `cap sync` 를 다시 돌리는데, 환경변수를 안 걸면 `http://localhost:9050` 이 구워진다 — 폰에서 localhost 는 «폰 자신»이다. 반드시 `npm run run:ios` / `run:android:ip` 같은 저장소 스크립트를 쓴다 | 빌드 산출물의 `App.app/capacitor.config.json` · `android/app/src/main/assets/capacitor.config.json` 를 **직접 열어본다** |

#### 🔑 ④ 는 오진이었다 — 무엇이 뒤집었나 (2026-08-06)

**원래 진단:** 「WKWebView 가 HTML5 Geolocation 을 지원하지 않는다. `@capacitor/geolocation` 이 필요하다.」
**근거로 삼은 관찰:** `simctl privacy grant` 로 OS 위치 권한을 «강제 부여»했는데도 실패했다.

🔴 **그 관찰은 두 가설 어느 쪽도 배제하지 못한다.** `navigator.geolocation`·서비스워커·웹푸시는
**보안 컨텍스트에서만** 동작하고, 예외는 `localhost` 뿐이라 **사설 IP 는 예외가 아니다.**
그리고 **보안 컨텍스트 차단은 OS 권한과 무관하게 걸린다** — 권한을 아무리 줘도 결과가 같다.
앱을 LAN IP 로 붙이면서 오리진이 `localhost` → 사설 IP 로 바뀐 것이 진짜 변화였다.

**뒤집은 실측 (시뮬레이터, `public/geo-check.html`):**

| 환경 | 오리진 | `isSecureContext` | `geolocation` | `serviceWorker` | 위치 요청 |
|---|---|---|---|---|---|
| 사파리 | `http://<LAN IP>:9050` | false | — | — | 🔴 팝업 없이 실패 |
| 사파리 | `https://<host>.local:9051` | **true** | 있음 | 있음 | ✅ **성공** `37.56650,126.97800 (±5m)` |
| **앱 웹뷰** | `https://<host>.local:9051` | **true** | **있음** | 🔴 **없음** | ✅ **권한 팝업 표시됨** |

🔑 **앱 웹뷰에서 «권한 팝업이 떴다»는 것이 결정적이다.** 지원하지 않는 API 는 팝업을 띄우지
않는다. (팝업의 「Allow」를 눌러 좌표까지 받는 것은 하지 않았다 — 시뮬레이터 팝업을 자동으로
누를 수 없어서다. **좌표 획득은 앱 웹뷰에서 아직 미확인**이고, 사파리에서는 확인됐다.)

**교훈:** 「권한을 줬는데도 안 된다 → 미지원이다」는 **권한 말고 다른 게이트가 없을 때만** 성립한다.
보안 컨텍스트가 정확히 그 다른 게이트였다. 실패가 「미지원」이 아니라 `code 1 (PERMISSION_DENIED)`
로 오는 것도 오진을 도왔다 — **권한 문제처럼 보이게 실패한다.**

→ 대응: 로컬 Docker 에 https(9051) 를 붙였다. 운영은 어차피 https(M-1)라 **웹 코드는 0줄 바뀌었다.**
절차·인증서·기기 CA 신뢰는 [`docker/apache/README.md`](../../../../docker/apache/README.md).

#### 🔑 웹이 앱보다 최신인 상태가 «정상»이다

`resources/js/native/bridge.js` 의 존재 이유는 감지가 아니라 **기능 협상**이다.
웹은 배포하면 즉시 갱신되지만 앱은 스토어 심사를 거쳐 천천히 갱신된다. 그 상태에서

전까지 복구할 수 없다.** 그래서 「앱이면 네이티브」가 아니라 **「그 앱이 그 기능을
아는가」**(`hasNativeCapability`)로 판정한다. 셸은 `window.__gps119Native =
{ version, capabilities }` 로 자기가 아는 기능을 알린다.

### M-12 를 왜 N0 로 올렸나 (2026-08-05 리뷰 반영)

원래 N3(네이티브 기능 구현)에 두었는데, **너무 늦다.** 이 답에 두 가지가 걸려 있다.

- **앱 분리 판단(N2)** — [`04 §5`](04-app-partitioning.md) 의 재검토 트리거 2·3 이 전부 «권한 요구 수준의 차이»라는 같은 축이다. 참가자에게도 「항상 허용」을 요구한다면 분리 압력이 커진다
- **스토어 제출물(N4)** — Play 백그라운드 위치 선언 양식과 iOS 목적 문자열이 «누구에게 무엇을 요구하는가»를 그대로 서술해야 한다

🔑 **다만 «확정»은 N0 에서 못 한다** — 참가자 권한 허용률이라는 실사용 데이터가 없기 때문이다. 그래서 둘로 쪼갠다.

| 단계 | 무엇 |
|---|---|
| **N0** | **잠정 방침 한 줄.** 권장 기본값: *"참가자·운영진 = 사용 중만 / 구급대·상황실 = 항상 허용"*. 근거 — 일반 참가자에게 상시 위치를 요구하면 설치율과 심사 통과율이 동시에 나빠진다 |
| **N3** | 실기기에서 **권한 허용률 관측** 후 확정. 참가자 허용률이 충분히 높고 현장에서 필요가 확인되면 상향 |
