### N1 — 서버: 푸시 발송 계층 — ✅ 대부분 완료 (2026-08-05)

**웹 푸시(VAPID)를 같이 넣어 앱 없이 검증 가능한 단위로 만든다.** 그대로 됐다.

#### ✅ 완료

| 1-1 | `device_tokens` + 등록/해제 API | 앱 토큰과 웹 구독을 한 표에. 조회·중복판정은 `token_hash`(unique)로만, 원문은 발송에만 |
| 1-2 | `PushService` + `PushSender` | «정책»과 «전송 규격»을 분리. `PushDelivery` 로 재시도(FAILED)와 폐기(INVALID)를 가른다 |

| 1-4 | 알림 종류 3종 + **연락처 미포함**(ADR-0004) | 모든 푸시 페이로드에 전화번호가 없는지 **테스트로 고정** |
| 1-5 | **웹 푸시(VAPID) 전 경로** | 키 생성 명령 · 서비스워커 `push`/`notificationclick` · 프로필 「알림 받기」 토글 |
| 1-6 | **`/control` `?project=` 딥링크** | 행사 상황실에게만 동작하지 않던 결함 해소 → [`03 §5-1`](03-push-notifications.md) |

> ⚠️ **1-0 을 먼저 한 이유** — 지금은 화면 한 칸이 틀리는 정도인 결함이 **푸시가 붙는 순간 전부 「폰이 잘못 울린다」로 승격**된다. 롤백된 지령이 브로드캐스트되면 「구급대원 폰이 울렸는데 지령이 없다」가 되고, 디스코드 실패로 잡이 재시도되면 「같은 신고로 폰이 두 번 운다」가 된다. 모델 훅 발행은 **팩토리로 행 하나만 만들어도 발송을 시도**하게 만든다.

> ⚠️ **VAPID 를 필수로 올린 이유(2026-08-05 검토)** — 원래 *"앱 없이도 웹 푸시로 검증 가능한 단위"* 라 써놓고 정작 웹 푸시를 «(선택)» 으로 뒀다. 선택이면 **N1 은 실기기 없이 검증할 방법이 없고**, N2 를 기다려야 하므로 "N1 을 N2 보다 먼저 둔다"는 순서 자체가 무의미해진다. 게다가 상황실은 PC 웹을 쓰므로([`04 §3-3`](04-app-partitioning.md)) **웹 푸시가 앱 푸시보다 먼저 필요하다.** → 실제로 그렇게 갔고, 덕분에 N2 없이 서버 경로를 끝까지 실측했다.

### M-12 를 왜 N0 로 올렸나 (2026-08-05 리뷰 반영)

원래 N3(네이티브 기능 구현)에 두었는데, **너무 늦다.** 이 답에 두 가지가 걸려 있다.

- **앱 분리 판단(N2)** — [`04 §5`](04-app-partitioning.md) 의 재검토 트리거 2·3 이 전부 «권한 요구 수준의 차이»라는 같은 축이다. 참가자에게도 「항상 허용」을 요구한다면 분리 압력이 커진다
- **스토어 제출물(N4)** — Play 백그라운드 위치 선언 양식과 iOS 목적 문자열이 «누구에게 무엇을 요구하는가»를 그대로 서술해야 한다

🔑 **다만 «확정»은 N0 에서 못 한다** — 참가자 권한 허용률이라는 실사용 데이터가 없기 때문이다. 그래서 둘로 쪼갠다.

| 단계 | 무엇 |
|---|---|
| **N0** | **잠정 방침 한 줄.** 권장 기본값: *"참가자·운영진 = 사용 중만 / 구급대·상황실 = 항상 허용"*. 근거 — 일반 참가자에게 상시 위치를 요구하면 설치율과 심사 통과율이 동시에 나빠진다 |
