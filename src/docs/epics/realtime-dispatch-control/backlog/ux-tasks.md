# DS lane — UX/화면 설계 태스크 백로그 (실시간 위치·지령 관제)

> 담당: lee-sunja (UX/UI). 이 파일은 [00-master-plan](00-master-plan.md)의 **DS-** lane을 실행 태스크로 분해한 것이다.
> 설계 문서(05/06/07/02/03)와 ADR(0002·0003·0004)을 다시 열지 않는다. 여기서는 **화면·플로우·상태·디자인 토큰** 산출물만 다룬다.
> 구현 코드는 짜지 않는다. 각 DS 태스크는 대응 FE 태스크보다 **한 발 앞서** 끝나야 한다(FE가 디자인 대기로 멈추지 않게 — 마스터플랜 §4 병목완화).

## 원칙 (전 태스크 공통 제약)

- **기존 톤 확장, 새 시스템 발명 금지.** Tailwind 4 + `rounded-2xl`/바텀시트/blue-accent 톤(`request/create.blade.php`), 뱃지 팔레트(amber/blue/emerald/slate), Enum 헬퍼 패턴(`label()`/`badgeClasses()`/`dotClass()`) 위에서 확장한다. 색·아이콘은 `EventRole`(02)·`RequestType`·`DispatchStatus`(03) enum 헬퍼에 귀속시켜 하드코딩하지 않는다.
- **ADR-0004(연락처 노출).** 신고자 이름·연락처는 **상황실(controller)·시스템 admin·"본인에게 배정된" 구급대원** 화면에서만 노출. 그 외(타 구급대원, 참가자, 관제 외 보드)에는 연락처 UI 컴포넌트 자체를 렌더하지 않는다. 모든 화면 스펙에 "연락처 노출 여부" 항목을 명시한다.
- **빈/로딩/에러 상태 필수.** 어떤 화면 스펙도 정상(happy) 상태만으로 FE에 넘기지 않는다. 위치권한 거부, WS 끊김(폴링 폴백), 약전계/오프라인, 가용 대원 0명 등 도메인 특유 상태를 반드시 정의한다.
- **긴급 도메인 가독성.** 긴급/신고 동선은 한 손·흔들리는 화면·햇빛 아래에서도 읽혀야 한다. 색만으로 의미 전달 금지(색맹 대비: 아이콘+라벨 병기).
- **산출물 형식.** 와이어프레임(저충실 ASCII/Figma 링크), 플로우(상태 다이어그램), 상태정의 표, 디자인 스펙(토큰·컴포넌트 규칙). Figma 파일은 링크로 두고 이 백로그엔 결정사항만 적는다.

## DS-0 — 디자인 토큰 · 역할/유형/지령 색상 시스템 (기반)

- **제목**: EventRole·RequestType·DispatchStatus 색상·아이콘 토큰 정의
- **대상**: 공통(참가자/구급대/관제 전부)
- **산출물**: 디자인 토큰 표(역할 7종·신고유형 4종·지령상태 6종 × 색/아이콘/라벨/명도대비), enum 헬퍼 매핑 명세(`markerColor()`/`markerIcon()`/`badgeClasses()`), 색맹 시뮬레이션 검증표
- **핵심 UX 요구**:
  - `EventRole` 7종(참가자/운영진/경찰/자봉코스/자봉구급/구급대/상황실) 각각 **지도 마커 색 + 아이콘 + 한글 라벨** 1세트. 인접 역할(자봉코스 vs 자봉구급, 구급대 vs 자봉구급)은 색만이 아니라 **아이콘 형태로도** 구분되게.
  - `RequestType`: 사고🔴/고장🟠/기타⚪/긴급🔴(05 문서 색). 긴급·사고가 둘 다 빨강이므로 아이콘/테두리로 분리.
  - `DispatchStatus` 6종(배정/수락/출동/도착/완료/거절) 뱃지·점(dot)·다음전이 색을 `RequestStatus` 뱃지 팔레트 연장선에서 정의.
  - 기존 amber/blue/emerald/slate 뱃지 톤과 **충돌 없이** 역할 7색을 추가(역할색은 마커 전용 팔레트로 분리해 상태 뱃지와 의미 혼동 방지).
- **수용 기준**:
  - [ ] 7역할 마커가 흑백 출력·색맹 시뮬(적록/청황)에서 상호 구별된다(아이콘 기여 포함).
  - [ ] 모든 색이 enum 헬퍼 1곳에 매핑되며 화면 스펙은 hex를 직접 쓰지 않는다.
  - [ ] 사고/긴급(동일 빨강)이 아이콘으로 구분된다.
- **의존**: Phase 1 / FE 참조: DS-1.1·DS-2.1 선행, FE-1.1·FE-2.1이 소비
- **규모**: S
- **Phase**: 1 (DS-1.1과 동시, 사실상 그 전제)

## DS-1.1 — 참가자 앱: 입장·역할표시·승인대기 플로우

- **제목**: 코드/QR 행사 입장 → 로그인 복귀 → 역할 표시 UX
- **대상**: 참가자 앱(PWA) — 전 역할 공통 진입
- **산출물**: 입장 플로우 다이어그램, 코드입력/QR스캔 화면 와이어, 역할표시·승인대기(`pending`) 화면 상태정의, 전화번호 미보유 분기(`require-phone` 계승) 와이어
- **핵심 UX 요구**:
  - 진입 2경로(6자리 코드 수동입력 / QR 스캔)를 한 화면에서. 코드는 대문자·숫자 혼동(0/O, 1/I) 입력 보조.
  - 미로그인 → 소셜/전화 로그인 후 **입력하던 코드 보존하고 복귀**(컨텍스트 유실 금지).
  - `join` 후 역할 상태 3분기: `active`(즉시 입장·역할 뱃지) / `pending`(승인대기 — "운영진 승인 후 권한 기능 사용 가능" 안내) / 전화번호 없음(입력 유도).
  - 역할 뱃지는 DS-0 토큰 사용. 권한 역할(구급대·상황실)이 `pending`이면 지령·관제 진입 버튼을 **잠금 상태로** 노출(왜 잠겼는지 설명).
- **수용 기준**:
  - [ ] 잘못된/만료된 코드, 로그인 취소 후 복귀, 전화번호 없음, 승인대기 — 4개 비정상 상태가 화면으로 정의됨.
  - [ ] 입장 직후 사용자가 "내가 이 행사에서 어떤 역할인지" 한눈에 안다.
- **의존**: Phase 1 / DS-0 선행. FE 참조: FE-1.1이 소비, DS-2.1(마커)이 역할토큰 이어받음
- **규모**: S
- **Phase**: 1

## DS-1.2 — 참가자 앱: 위치공유 권한 온보딩 · 공유 토글

- **제목**: 위치권한 온보딩과 상시 공유 상태 표현
- **대상**: 참가자 앱(PWA) — 전 역할(구급대 위치공유 모듈도 공유)
- **산출물**: 권한요청 온보딩 시퀀스(허용 전/거부/재요청), 상단 공유 토글 컴포넌트 스펙, 공유 ON/OFF/일시강제ON 상태정의, 오프라인·약전계 표시
- **핵심 UX 요구**:
  - 입장 후 **자동 위치공유 시작**이 원칙이나(05), 브라우저 권한 팝업 전 "왜 위치가 필요한지" 1스텝 사전 설명(권한 거부율 낮추기).
  - 권한 거부 시: 기능 차단 대신 **재요청 경로 + 수동 위치입력 폴백** 안내(긴급 도메인 — 차단은 위험).
  - 공유 토글: 끄면 개인정보 보호(`sharing_location=false`)지만 **신고 시엔 일시 강제 ON**됨을 토글 옆에 명시(사용자가 놀라지 않게).
  - 상태 표현: 공유중(초록 점)·꺼짐(회색)·신고로 임시ON(점멸)·오프라인/약전계(주의색 + "위치 전송 지연중, 복구 시 재전송"). online/offline은 색+텍스트 병기.
- **수용 기준**:
  - [ ] 권한 거부·약전계·오프라인 3상태가 사용자에게 명확히 구분되어 보인다.
  - [ ] "공유를 꺼도 신고하면 잠시 켜진다"는 사실이 토글 시점에 전달된다.
- **의존**: Phase 2 / DS-1.1 이후. FE 참조: FE-2.2(watchPosition 토글)가 소비
- **규모**: S
- **Phase**: 2

## DS-2.1 — 웹 관제 레이아웃 정밀화 (대화면)

- **제목**: 관제 화면 — 역할필터·실시간지도·신고목록·출동현황보드 레이아웃 정밀화
- **대상**: 웹 관제(PC 대화면, Vue SPA)
- **산출물**: 07 ASCII 레이아웃의 고충실 와이어프레임, 4영역 그리드 스펙(반응형 최소폭·패널 접힘), 영역별 빈/로딩/에러 상태, 헤더 KPI(온라인 N·신고 N) 스펙
- **핵심 UX 요구**:
  - 07 레이아웃(상단바 + 좌측 역할필터 + 중앙 지도 + 하단 신고목록/출동보드)을 정밀화. 지도가 화면의 주인공, 목록·보드는 종속 패널.
  - 좌측 **역할 필터** 7체크박스 = DS-0 마커색 칩과 1:1(필터 항목 옆에 마커색 미리보기). 즉시 토글, 0개 선택 시 안내.
  - **신고 접수 목록**: `request.created` 실시간 prepend. 행마다 유형 아이콘·시각·상태 뱃지·[배정] CTA. **연락처는 행 펼침(상세) 시에만 노출**(ADR-0004 — 관제는 노출 허용).
  - **출동 현황 보드**: 배정/출동/도착/완료 실시간 카운트 + (선택)타임라인. DispatchStatus 색 사용.
  - 빈 상태: 신고 0건("아직 접수된 신고가 없습니다"), 인원 0명, 행사 미선택. 로딩: 지도 타일·마커 초기로드 스켈레톤. 에러: WS 끊김 배너(폴링 폴백중 표시).
- **수용 기준**:
  - [ ] 4영역이 1920·1440 폭에서 무너지지 않고, 좁아지면 패널이 접힌다.
  - [ ] 역할 필터 토글이 즉시 지도 마커에 반영되는 인터랙션이 정의됨.
  - [ ] 신고 행 펼치기 전에는 연락처가 보이지 않는다(ADR-0004 반영).
- **의존**: Phase 2 / DS-0·DS-1.1 선행. FE 참조: FE-2.1(관제 SPA v1)이 소비 — **크리티컬 패스 병목 FE-2.1을 막지 않도록 최우선**
- **규모**: M
- **Phase**: 2

## DS-2.2 — 관제 지도: 마커 시스템 · 클러스터링 · 고정핀/이동마커 규칙

- **제목**: 역할별 마커, 신고 고정핀 vs 인원 이동마커, 대규모 클러스터링 표시 규칙
- **대상**: 웹 관제(지도 레이어)
- **산출물**: 마커 디자인 스펙(역할 7종·온오프라인·선택 상태), 신고 고정핀(점멸) vs 인원 이동마커 시각 구분 규칙, 클러스터링 표시 규칙(임계·뱃지·확대 전이), 마커 범례
- **핵심 UX 요구**:
  - **신고 위치 = 고정 핀(점멸)** vs **인원 = 이동 마커**를 형태로 명확히 구분(07: 신고는 점멸 핀, 출동중 구급대원은 이동 마커). 고정핀은 신고 스냅샷 좌표(03 불변)임을 시각적으로 "땅에 박힌" 형태로.
  - online/offline: `last_seen_at` 타임아웃 → 마커 흐리게(투명도)·라벨 처리. 제거 타이밍 규칙 정의.
  - **대규모(수백~수천)**: 뷰포트 클러스터 — 클러스터 버블에 인원수 + (가능하면)역할 구성 미니표시, 확대 시 분해 전이. 신고 핀은 **클러스터에 묻히지 않고** 항상 위(z) 노출.
  - 마커 클릭 → 인원(역할·online·연락처 없음) / 신고(유형·시각·[배정], 연락처는 관제 권한 시) 인포윈도 분기.
  - 색맹 대비: 마커는 색+아이콘, 선택 마커는 외곽 링으로 강조(색 의존 금지).
- **수용 기준**:
  - [ ] 신고 핀과 인원 마커가 색을 무시해도 형태만으로 구분된다.
  - [ ] 1000+ 마커 시 클러스터 규칙(병합·분해·신고핀 예외)이 정의됨.
  - [ ] 마커는 좌표만 이동(전체 리렌더 금지)을 전제로 한 상태 표현이다(03/07).
- **의존**: Phase 2 / DS-2.1 이후. FE 참조: FE-2.1이 소비
- **규모**: M
- **Phase**: 2

## DS-3.1 — 참가자 신고: 유형 버튼 · "이 위치가 맞습니까?" 주소확인 모달 ★핵심

- **제목**: 사고/고장/기타/긴급 버튼 + 주소확인 모달(기존 `confirm` 대체)
- **대상**: 참가자 앱(PWA)
- **산출물**: 신고 버튼 4종 스펙(`RequestType` 색·아이콘), **주소확인 모달 풀 와이어**(주소+지도미리보기+보정), 신고 동선 플로우, 긴급전화 즉시 `tel:` 분기, 모달 빈/로딩/에러 상태
- **핵심 UX 요구**:
  - 버튼: 사고🔴/고장🟠/기타⚪/긴급🔴 — DS-0 RequestType 토큰. 한 손 도달 가능 영역(바텀시트 하단), 오탭 방지 간격, `:active` 스케일(기존 `.emergency-btn` 톤 계승).
  - **주소확인 모달(이 태스크의 심장)**: 기존 `RequestMapApp.js` 146행 `confirm('위치공유를 하시겠습니까?')`를 대체. 구성: ① 역지오코딩된 **주소 텍스트(크게)** ② **지도 미리보기(핀)** ③ 좌표 미세보정(드래그/주소재검색) ④ [이 위치로 신고]/[취소]. "이 위치가 맞습니까?"가 질문의 핵심 — 잘못된 좌표로 구조대가 출동하는 최악을 막는 마지막 게이트.
  - 모달 상태: 역지오코딩 **로딩**(주소 변환중 스피너), **실패**(주소 못 찾음 → 좌표만 + 수동주소 입력 폴백, 신고는 가능하게), GPS 저정확도(accuracy 큰 값 → "위치 정확도 낮음, 지도에서 확인" 경고).
  - **긴급전화**는 모달 없이 즉시 `tel:`(행사 구조본부 번호, `projects.settings`). 다른 3유형과 동선이 다름을 버튼에서 시각 구분.
  - 신고는 `type` enum 전송(기존 free-text `description` 대체) — 버튼이 곧 유형.
- **수용 기준**:
  - [ ] 신고 전 주소확인 모달에 **주소 텍스트가 표시**된다(05 수용기준).
  - [ ] 역지오코딩 실패·저정확도에도 신고가 막히지 않는 폴백이 있다.
  - [ ] 긴급전화는 모달 없이 즉시 전화 연결로 분기된다.
  - [ ] 단순 `confirm`이 아니라 지도+주소 모달임이 와이어로 확정.
- **의존**: Phase 3 / DS-0 토큰. FE 참조: FE-3.1이 소비(BE-3.1 `type` 마이그레이션 후)
- **규모**: M
- **Phase**: 3

## DS-3.2 — 참가자: 신고 접수완료 · 담당자 전화연결 · 내 신고 상태추적

- **제목**: 접수완료 화면 → 담당자 `tel:` 연결 → 상태 실시간 추적
- **대상**: 참가자 앱(PWA)
- **산출물**: 접수완료 화면 와이어, 상태 추적 화면(대기→진행중→완료 타임라인) 상태정의, 담당자 정보·전화연결 버튼 스펙, 배정 전/후 연락처 분기
- **핵심 UX 요구**:
  - 접수 직후 "신고가 접수되었습니다" 확정 피드백 + 신고 위치 재확인(고정좌표) + 카카오맵/내비 보기.
  - **담당자 전화연결**: 구급대원 배정(`request.status.updated`) 수신 시 담당자 이름 + `tel:` 버튼. **배정 전에는 행사 상황실 대표번호**로 연결(공백 없이). 신고자는 자기 신고의 담당자 연락처만 봄(ADR-0004 — `requester` 채널은 담당자 정보만).
  - **상태 추적**: `event.{projectId}.requester.{userId}` 구독으로 대기→진행중→완료 실시간 갱신. DispatchStatus와 매핑된 타임라인(접수→배정→출동→도착→완료). 각 단계 시각 표기.
  - 상태별: 대기(접수됨, 곧 배정)·진행중(담당자 출동중, 전화버튼 강조)·완료(처리됨). WS 끊김 시 폴링 폴백 + "갱신 지연중" 표시.
  - **자가취소 불가** 도메인 정책 반영: 취소 버튼 대신 "취소가 필요하면 상황실로 전화" 안내(기존 정책 계승).
- **수용 기준**:
  - [ ] 배정 전/후 전화연결 대상(상황실→담당자)이 자연스럽게 전환된다.
  - [ ] 대기/진행중/완료가 실시간으로 추적되고 끊김 시 폴백이 표시된다.
  - [ ] 신고자 화면엔 담당자 정보만 노출(다른 인원 연락처 없음 — ADR-0004).
- **의존**: Phase 3 / DS-3.1 이후. FE 참조: FE-3.4가 소비
- **규모**: S
- **Phase**: 3

## DS-3.3 — 구급대 앱: 지령 풀스크린 수신 · 상태머신 버튼 · 거절사유 · 카카오내비

- **제목**: 지령 풀스크린 알림(음/진동) + 수락→출동→도착→완료 상태전이 UX + 거절사유 + 내비 진입
- **대상**: 구급대 앱(PWA)
- **산출물**: 지령 풀스크린 알림 와이어(알림음/진동 트리거 명세), 상태머신 버튼 UX(전이별 라벨·색·확인), 거절 사유 입력 화면, 카카오내비 진입(고정좌표) 분기, 각 전이 빈/로딩/에러 상태
- **핵심 UX 요구**:
  - **풀스크린 수신**: `dispatch.assigned` 시 화면 점유 + 알림음/진동(주의 환기). 카드 정보: 신고유형(아이콘)·신고 위치(주소+지도)·**신고자 이름·연락처(본인 배정건이므로 노출 — ADR-0004 `dispatch` 채널)**·상황실 메모. 운전중·장갑 낀 손 가정 → 큰 터치 타깃.
  - **상태머신 버튼**(`DispatchStatus` 전이): [수락]→accepted, [출동]→en_route(+카카오내비 자동제안), [도착]→arrived, [완료]→completed(+처리메모). **현재 단계의 다음 전이 버튼만 크게 노출**(잘못된 전이 원천 차단 — 03 전이검증 UI 표현). 진행중 단계는 타임스탬프로 표시.
  - **거절**: assigned/accepted 단계에서만. **사유 필수**(사유 미입력 시 거절 불가) — 재지령 판단 근거. 사유 프리셋(이미 출동중/너무 멈/장비없음/기타).
  - **카카오내비**: "출동" 시 신고 **고정 스냅샷 좌표**로 `kakaonavi://` 딥링크, 미설치 시 카카오맵 웹 폴백(신고자 실시간 위치 아님 — 06/03 강조).
  - 에러: 전이 거부됨(서버 검증 실패)·네트워크 실패 시 재시도·내비 앱 부재 폴백.
- **수용 기준**:
  - [ ] 지령 수신이 풀스크린+음/진동으로 즉시 인지된다.
  - [ ] 다음 전이 버튼만 노출되어 잘못된 전이가 UI에서 불가능하다.
  - [ ] 거절은 사유 없이는 제출되지 않는다.
  - [ ] "출동"에서 고정좌표 카카오내비가 열리고 미설치 폴백이 있다.
  - [ ] 신고자 연락처는 본인 배정 지령 카드에서만 보인다(타 신고 보드 없음 — ADR-0004).
- **의존**: Phase 3 / DS-0 토큰·DS-3.1. FE 참조: FE-3.2(구급대 end-to-end, 크리티컬 패스 종착)가 소비
- **규모**: M
- **Phase**: 3

## DS-3.4 — 관제: 지령 배정 인터랙션 · 출동 현황 보드

- **제목**: 신고→가용 대원(거리순) 배정 UI + 출동 현황 실시간 보드
- **대상**: 웹 관제(+ 모바일 축약형, 06 상황실 화면)
- **산출물**: 배정 패널 와이어(신고 클릭 → 가용 대원 거리순 리스트 → 선택+메모 → 발령), 출동 현황 보드 스펙(카운트+타임라인), 재배정/회수 동선, 가용 대원 0명 빈 상태
- **핵심 UX 요구**:
  - 신고 클릭 → 배정 패널: 가용 구급대원(역할=paramedic/volunteer_medic, online) **거리순** 리스트(거리·현재상태 표시). 대상 선택 + 메모 → 발령. *(가용성 정렬 기준은 열린결정 Q3 — 거리만 vs 지령보유수: 두 정렬 모두 수용 가능한 리스트 컴포넌트로 설계.)*
  - 발령 후: 해당 신고가 "배정됨"으로 전환, 대원 마커에 배정 표시. **거절/무응답 시 재배정** 동선(다른 대원에게 재지령 — 06).
  - **출동 현황 보드**: `dispatch.updated` 실시간 배정/출동/도착/완료 카운트 + 처리시간(접수→도착→완료) 표기. 완료 지령은 이력으로 이동.
  - 연락처는 관제(controller/admin) 화면이므로 신고 상세에서 노출 허용(ADR-0004).
  - 빈/에러: **가용 대원 0명**("배정 가능한 구급대원이 없습니다" + 전체 호출/대기 안내), 발령 실패 재시도, 무응답 타임아웃 시각 알림.
- **수용 기준**:
  - [ ] 신고에서 대원을 거리순으로 골라 배정하는 동선이 정의됨.
  - [ ] 가용 대원 0명·거절·무응답(재배정) 상태가 화면으로 정의됨.
  - [ ] 출동 현황이 실시간 카운트+처리시간으로 표현된다.
- **의존**: Phase 3 / DS-2.1·DS-3.3. FE 참조: FE-3.3이 소비
- **규모**: M
- **Phase**: 3

## DS-4.1 — 공통: 온라인/오프라인 · 빈·로딩·에러 상태 시스템 · PWA 설치 온보딩

- **산출물**: 상태 컴포넌트 라이브러리(빈/로딩 스켈레톤/에러/오프라인 배너) 스펙, online/offline 표현 통일 규칙, PWA 설치 유도 온보딩 와이어, 알림 권한 요청 시퀀스

  - 빈/로딩/에러를 화면마다 따로 만들지 않게 **재사용 컴포넌트 1세트**(스켈레톤·일러스트·재시도 버튼)로 정의.

- **수용 기준**:

  - [ ] PWA 설치·권한 유도가 강압적이지 않게(디스미스 가능) 설계됨.
- **의존**: Phase 4 / 전 DS 태스크의 상태정의를 수렴. FE 참조: FE-4.1(PWA 마감)이 소비
- **규모**: S

## DS-4.2 — 검토: 통합 사용성·접근성 QA (출시 게이트)

- **제목**: 3앱 통합 UX/접근성 QA 리포트
- **대상**: 공통(참가자/구급대/관제 구현물)
- **산출물**: UX QA 리포트(시각 일관성·디자인시스템 정합·AI슬롭 점검), 접근성 체크(색맹 대비·키보드·스크린리더·긴급 가독성), 우선순위 붙인 개선 백로그
- **핵심 UX 요구**:
  - 구현 결과물이 DS-0 토큰·기존 톤과 일치하는지(재작업 비율 KPI), 일회성 패턴 남발 점검.

  - [ ] 연락처 노출이 ADR-0004 범위를 벗어나는 화면이 0건.
  - [ ] 개선점이 우선순위(심각/중/경)와 함께 정리됨.
- **의존**: Phase 4 / FE-3.x·FE-4.1 구현 후. FE 참조: 전 FE 결과물

## DS lane 의존 요약

```
DS-0(토큰) ─┬─ DS-1.1(입장) ── DS-1.2(위치토글)
            ├─ DS-2.1(관제레이아웃) ── DS-2.2(마커/클러스터)
            └─ DS-3.1(신고모달★) ─┬─ DS-3.2(추적/전화)
                                   ├─ DS-3.3(구급대 지령★)
                                   └─ DS-3.4(배정/보드)
모든 상태정의 → DS-4.1(공통상태/PWA) → DS-4.2(QA 게이트)
```

> DS lane은 항상 대응 FE보다 한 발 앞선다. 특히 **DS-2.1**(→FE-2.1 관제 SPA, 크리티컬 패스 병목)과 **DS-3.1·DS-3.3**(→FE-3.1·FE-3.2 핵심가치)은 절대 후행 FE를 막지 않도록 우선 착수한다.
